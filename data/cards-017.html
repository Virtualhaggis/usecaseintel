Astro SSRF (CVE-2026-25545) — Node.js egress fetch for /404.html or /500.html with UA 'node' AIExploitation High
Hunts the server-side fetch the Astro SSR engine emits when its prerenderedErrorPageFetch() is hijacked via a spoofed Host header. The Astro server (Node.js) will egress an HTTP GET to an attacker-controlled host for /404.html or /500.html with the default Node fetch User-Agent 'node' — a fingerprint shown verbatim in the Aikido write-up and reproducible from the GHSA-qq67-mvv5-fw3g PoC. This is the SSRF call going out, before the attacker's redirect pivots it to an internal target. Rationale: Article-specific indicators: the Aikido write-up shows the exact outbound request the vulnerable Astro server emits — GET /404.html (or /500.html) with User-Agent: node — and the GHSA-qq67-mvv5-fw3g advisory plus the GitLab advisory entry confirm the PoC behavior. The combination of Node UA + the specific URI suffix + non-private destination is extremely high-fidelity because no legitimate Astro deployment should be requesting another host's error pages. Cross-checked against: • https://github.com/withastro/astro/security/advisories/GHSA-qq67-mvv5-fw3g • https://advisories.gitlab.com/pkg/npm/@astrojs/node/CVE-2026-25545/ • https://nvd.nist.gov/vuln/detail/CVE-2026-25545 • https://www.sentinelone.com/vulnerability-database/cve-2026-25545/

Astro SSRF (CVE-2026-25545) — inbound Host header mismatch with 4xx/5xx response (trigger) AIDelivery Medium
Hunts the inbound trigger half of CVE-2026-25545: an HTTP request to the Astro origin whose Host header value differs from the server's canonical hostname and which returns 404/500 (the status that drives renderError() into the vulnerable prerenderedErrorPageFetch path). Tune by populating the allowed-hosts list with your Astro app's legitimate hostnames; everything else is a likely Host-header-injection probe. Rationale: Article-specific: CVE-2026-25545 requires the attacker to set the Host header to a value the Astro server doesn't own and trigger an error page (article states `curl -i 'http://localhost:4321/not-found' -H 'Host: attacker.tld'`). Joining 4xx/5xx response status with non-canonical Host header at the origin captures the trigger event. Sigma omitted because the detection requires an allowlist comparison (not single-event-shape); Defender KQL omitted because Defender XDR has no equivalent web-tier telemetry for Host header values. Datadog omitted because none of the canonical sources in our schema cover Astro origin web logs. Cross-checked against: • https://github.com/withastro/astro/security/advisories/GHSA-qq67-mvv5-fw3g • https://advisories.gitlab.com/pkg/npm/@astrojs/node/CVE-2026-25545/ • https://www.aikido.dev/blog/astro-full-read-ssrf-via-host-header-injection
