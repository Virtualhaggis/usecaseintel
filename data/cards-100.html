Celery task injected into Apache Airflow message broker (unacked queue / execute_command) AIDelivery High
Hunts a process pushing a forged Celery task into the Airflow message broker (Redis unacked hash or AMQP) to trigger worker RCE per CVE-2020-11981/11982. Anchors on broker write verbs (LPUSH/HSET) combined with Airflow Celery task markers (celery_executor.execute_command, unacked) that a legitimate operator would never type by hand. Rationale: Anchors on the article's exact broker artifacts (unacked Redis hash, airflow.executors.celery_executor.execute_command task name) paired with Redis/AMQP write verbs; a human running redis-cli LPUSH with a Celery task payload is the documented exploit primitive for both CVEs. Cross-checked NVD CVE-2020-11981 and GitHub Advisory GHSA-9g2w-5f3v-mfmm. Cross-checked against: • https://nvd.nist.gov/vuln/detail/cve-2020-11981 • https://github.com/advisories/GHSA-9g2w-5f3v-mfmm • https://security.snyk.io/vuln/SNYK-PYTHON-APACHEAIRFLOW-570291

Apache Airflow Celery worker spawns non-airflow child (command-injection RCE, CVE-2020-11981) AIExploitation High
Hunts the post-exploitation signal of CVE-2020-11981: an Airflow Celery worker directly executing a broker-supplied command that is NOT an 'airflow tasks run' subprocess. Legit workers always fork into 'airflow ... run'; a direct shell/LOLBin child of the worker is the injected command running. Rationale: Uses the article's documented exec path: the Celery worker (airflow worker -q test) normally forks into 'airflow tasks run', so a direct shell/LOLBin child of the worker is the injected broker command from CVE-2020-11981. The airflow-subprocess exclusion is the discriminator that strips BashOperator noise. Corroborated by NVD CVE-2020-11981. Cross-checked against: • https://nvd.nist.gov/vuln/detail/cve-2020-11981 • https://security.snyk.io/vuln/SNYK-PYTHON-APACHEAIRFLOW-570291

Apache Airflow task run with --pickle flag (pickle deserialization, CVE-2020-11982) AIExploitation Medium
Hunts execution of an Airflow task via the --pickle code path, the deserialization vector behind CVE-2020-11982 where Celery workers unpickle broker data. Post-fix (>=1.10.11) pickle is disabled by default, so an 'airflow run ... --pickle <id>' invocation is anomalous and worth surfacing. Rationale: Anchors on the article's verbatim task command ['airflow','run','exp','sleep',...,'--pickle','15',...] (the base64 unacked body decodes to exactly this), making --pickle the high-fidelity deserialization marker for CVE-2020-11982. Confirmed via GitHub Advisory GHSA-9g2w-5f3v-mfmm (insecure accept_content [json,pickle] default). Cross-checked against: • https://github.com/advisories/GHSA-9g2w-5f3v-mfmm • https://www.miggo.io/vulnerability-database/cve/CVE-2020-11982
ATT&CKT1190 T1059.006
Data sourcesEndpoint.Processes
Expected false positives · estimated rate: medium — model-assessed, tune to your environment
  • Legacy Airflow deployments (<1.10.11) intentionally running with donot_pickle=False where --pickle is the normal scheduler-to-worker mechanism
  • Operators that explicitly set 'airflow run --pickle' during DAG debugging
  • Backfill/test harnesses invoking tasks with pickled DAG IDs in non-prod
  • Custom Airflow plugins that pass --pickle for serialized DAG transport
Response runbook
1) Triage: confirm the Airflow version on the host (>=1.10.11 means pickle should be off — treat as suspicious) and identify whether the --pickle id maps to a known DAG run or an unscheduled task. 2) Contain: if unsanctioned, isolate the worker, set core.donot_pickle=True / restrict Celery accept_content to json, and rotate broker credentials. 3) Hunt: correlate to broker-injection and worker-child UCs on the same host, and review the worker for unexpected child processes spawned immediately after the --pickle task.

Prototype pollution payload in CLI args (--__proto__ / constructor.prototype) to Node tool AIExploitation High
Hunts for the minimist CVE-2020-7598 exploitation primitive: command-line argument tokens that walk the Object prototype (--__proto__.shell, __proto__.polluted, constructor.prototype.x) passed to a Node.js CLI utility. These tokens are JavaScript keywords that essentially never appear in legitimate command lines, making them a high-fidelity indicator of an attacker abusing an argument parser (minimist/yargs-parser) to pollute Object.prototype for privilege escalation or logic tampering. Rationale: Anchored on the exact exploit token from the article (`--__proto__.shell`) and the corroborated CVE-2020-7598 payload family (`--__proto__.y=`, `--constructor.prototype.polluted=true`). These JS-keyword tokens in argv are near-zero-FP. Cross-checked GitHub Advisory GHSA-vh95-rmgr-6w4m and SentinelOne's CVE DB for payload syntax. World-writable executable run as a shell (-c) — minimist polluted shell privesc payload AIInstallation Medium
Hunts the second stage of the CVE-2020-7598 privilege-escalation chain from the article: after polluting Object.prototype.shell, child_process.execSync invokes the attacker file (e.g. /tmp/exploit) as the system shell, spawning it as `<world-writable-path> -c <command>`. A binary living in /tmp, /var/tmp or /dev/shm being executed with shell `-c` semantics is a strong signal of execSync shell-substitution, distinct from a normal script launch. Rationale: Anchored on the article's exact privesc payload: `printf '#!/bin/sh id' > /tmp/exploit; chmod +x /tmp/exploit; u-reboot --__proto__.shell /tmp/exploit`, where the polluted shell makes execSync run /tmp/exploit as `-c` shell. The world-writable-path + shell-`-c`-invocation pair is the distinguishing behaviour, separate from the argv token in UC1. Rationale: Anchors on the article's exact exploitation channel — AJP on TCP/8009.
